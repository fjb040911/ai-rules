# Initialization

1. Inspect .ai-rules before writing. If present, read config.json, rules-config.json, .ai-rules.md, and their inheritance. Preserve custom rules, disabled/enabled choices, exceptions, and paths. Fill only missing items that are justified; explain conflicts rather than replacing valid settings. Invalid JSON requires a focused repair, not a reset.
2. Inspect manifests and representative source directories to identify language/framework, project root, source roots, and architectural boundaries. For monorepos, identify package boundaries. Ask about ambiguous scope or team requirements that cannot be inferred. Use a host question tool if available, otherwise concise chat questions. In automatic mode use defensible defaults and disclose assumptions; do not guess critical business constraints.
3. Read assets/templates/index.json relative to the installed skill root. Choose the matching template. Framework templates already include their base rules. Prefer zh-CN for Chinese conversations and en otherwise; other requested languages can be translated by the agent while preserving rule IDs and detection expressions. These are agent translations, not bundled translations.
4. For a new configuration copy the chosen template's three files into project .ai-rules/. Use host file tools, not a required script. For unsupported stacks, derive a small set of justified project rules from observed conventions and label them as project-derived. For multiple stacks, combine relevant rules with unique IDs, merge configuration according to config-spec.md, and map each rule scope to appropriate source paths; don't silently review only one package.
5. Edit project .ai-rules/config.json to map aliases used by selected rules to real project-relative directories. Check references in detect.where and context. Do not create business directories to satisfy an alias. If a boundary is absent, map to an existing appropriate directory or adapt the affected rule with an explanation. Set include/exclude based on actual source roots; remember inherited include/exclude arrays are additive. To narrow an existing inherited include set, edit its defining configuration rather than adding a narrower override.
6. Use config-spec.md to check all enabled rule IDs, JSON syntax, inheritance references, aliases, scopes, and path existence. Create .ai-rules/cache only if an artifact needs it. Do not create placeholder evidence or installation manifests. If ai-law is already available, optionally run ai-law doctor for additional validation; do not call its interactive init.
7. Show created/updated files, chosen stack, assumptions, mappings, and unresolved items. On repeat initialization make only necessary changes. Never overwrite a customized rule set with a template wholesale. Do not change host permission settings or install provider workflows as a side effect.
