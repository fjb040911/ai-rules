# AI-RULES express

version: 0.1.0
stack: express

### RULE: NODE-ARCH-101
severity: FATAL
scope: transport
intent: 面向传输层的 Node.js 模块不得直接导入 repository 或原始数据客户端。

detect:
  import: @repositories/**
  where: importer in @transport/**
fix: 将持久化访问移动到 service 模块，并让 transport 层依赖 service 而不是 repository。
prompt:
  violation: 某个面向传输层的 Node.js 模块直接导入了 repository 或原始数据客户端。
  requirement: 路由、控制器和 handler 必须通过 service 间接访问持久化层。
  solution: 把数据访问逻辑迁移到 service 中，再由 transport 层注入或导入该 service。
context:
  - @services
  - @repositories

### RULE: NODE-ARCH-102
severity: WARN
scope: transport
intent: 传输层 handler 应保持轻量，不应在一个函数里混合校验、编排、持久化和响应格式化。

detect:
  semantic: request or message handlers contain orchestration, validation, persistence, and response formatting in the same function instead of delegating to service modules
fix: 拆分请求接线与业务编排，把可复用逻辑移动到 service 模块。
prompt:
  violation: 某个传输层 handler 看起来内联了过多职责。
  requirement: 传输层代码应保持轻量，并把业务编排委托给 service。
  solution: 抽离校验、编排和持久化逻辑到 service，handler 仅保留传输层职责。
context:
  - @transport
  - @services

## Reliability And Security

### RULE: NODE-ERR-201
severity: WARN
scope: reliability
intent: 异步 handler 应把错误传递给集中错误处理，而不是在本地吞掉。

detect:
  semantic: async handlers catch errors, log them, or ignore them without forwarding to centralized error handling
fix: 把错误转发给集中式中间件或框架错误边界，避免空 catch 或只打印日志的 catch。
prompt:
  violation: 某个异步 Node.js handler 看起来吞掉了错误或把错误埋在本地。
  requirement: 异步 handler 的失败必须进入集中错误处理链路。
  solution: 重新抛出错误、调用 next(error) 或交给框架错误边界，而不是直接吞掉失败。
context:
  - @middleware
  - @transport

### RULE: NODE-SEC-202
severity: FATAL
scope: security
intent: Node.js 服务日志不得泄露敏感凭据与 token。

detect:
  regex: "(console\\.(log|error|warn)|logger\\.(info|warn|error|debug)).*(password|token|secret|authorization|cookie)"
  where: filePath in @src/**/*.{js,ts}
fix: 在日志输出前删除或脱敏敏感值，并集中封装安全日志 helper。
prompt:
  violation: 某条日志语句看起来暴露了凭据或安全敏感字段。
  requirement: 日志不得泄露 password、token、cookie 或 authorization 等敏感数据。
  solution: 对敏感字段做脱敏或移除，并改用安全的结构化日志 helper。
context:
  - @config
  - .env.example

### RULE: NODE-PERF-301
severity: WARN
scope: reliability
intent: 出站网络调用应设置显式超时、abort signal 或有界重试策略。

detect:
  semantic: outbound HTTP or RPC calls are created without explicit timeout, abort signal, or bounded retry policy
fix: 为出站 HTTP/RPC 客户端增加 timeout、abort 和有界 retry 控制。
prompt:
  violation: 某个出站 Node.js 网络路径看起来缺少超时或有界重试控制。
  requirement: 外部调用必须有明确失败边界，不能无限挂起。
  solution: 补充 timeout/abort 控制，并让 retry 保持有界且可观测。
context:
  - @services
  - @config

### RULE: EXPRESS-301
severity: WARN
scope: transport
intent: Express 路由处理函数应保持轻量，并把业务工作流委托给 service。

detect:
  semantic: express route handlers contain business branching, persistence logic, and response formatting inline instead of delegating to services and middleware
fix: 把编排和业务分支从 route callback 中移出，交给 service 或 middleware。
prompt:
  violation: 某个 Express 路由处理函数看起来内联了较重的业务流程。
  requirement: 路由处理函数应聚焦请求接线，并把业务工作流委托出去。
  solution: 把重逻辑抽到 service 中，让 middleware/handler 只负责 transport 层职责。
context:
  - @routes
  - @services

### RULE: EXPRESS-302
severity: WARN
scope: reliability
intent: Express handler 不应在发送响应后继续执行隐式控制流。

detect:
  semantic: express handlers send a response and continue control flow without return or next(error), creating double-send or hidden fallthrough risk
fix: 在 res.send/res.json/res.end 或 next(error) 后显式结束控制流，避免 fallthrough。
prompt:
  violation: 某个 Express handler 看起来有响应发送后继续执行的风险。
  requirement: 响应终止必须是显式的，避免 handler 在响应后继续执行。
  solution: 增加显式 return，或调整控制流结构，确保响应结束后没有意外继续执行的路径。
context:
  - @routes
  - @middleware
