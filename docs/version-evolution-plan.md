# AI-RULES Version Evolution Plan

> This document defines the recommended evolution path after `v0.6.0`. It assumes `v0.5.7` completed the high-value rule expansion, `thresholds`, and `exceptions`, and `v0.6.0` completed project-layout configuration hardening through `config.json`, path aliases, alias warnings, and stronger AI prompt guidance.

---

## 1. Current Baseline

AI-RULES is no longer only a prompt template generator. The current baseline includes:

- rule/config parsing
- config inheritance merge
- local evidence collection for `regex` and `import/include`
- AI-guided handling for `ast` and `semantic` rules
- `thresholds` and `exceptions` config support
- optional `config.json` sidecar support for project-specific layout overrides
- path alias resolution in `context`, `detect.where`, `detect.import`, and `detect.include`
- visible warnings when configured path aliases do not match the local repository layout
- rule-aware audit prompt generation
- report normalization and validation
- enriched fix prompt generation
- high-value frontend, Python/FastAPI, and Java/Spring rules

The next versions should focus less on adding more rules and more on improving the CLI's ability to explain, measure, and link evidence.

---

## 2. Evolution Principle

The core principle is:

**Do not jump directly from rule templates to a full static analyzer.**

Instead, evolve through small vertical slices:

1. Make the CLI explain what it will check.
2. Add lightweight deterministic evidence where it is cheap and reliable.
3. Strengthen report/evidence linkage.
4. Add AST support only after the evidence pipeline is stable.
5. Expand templates and platform features after the core model is proven.

This keeps every version useful and avoids a risky big-bang rewrite.

## 3. Version Path

## v0.6.0: Project Layout Config And Rule Consumption Hardening

### Status

Implemented as the current improvement version.

### Scope

- Add optional `.ai-rules/config.json` sidecar support
- Move template path aliases out of `rules-config.json`
- Resolve aliases before audit/fix prompt generation
- Resolve aliases in:
  - `context`
  - `detect.where`
  - `detect.import`
  - `detect.include`
- Warn prominently when configured aliases point to paths that do not exist
- Strengthen prompt guidance so AI agents consume:
  - `.ai-rules/rules-config.json`
  - `.ai-rules/config.json`
  - `.ai-rules/.ai-rules.md`
- Update docs and tests

### Acceptance Criteria

- Users can adapt generated rules to non-standard project layouts by editing `.ai-rules/config.json`
- `audit` and `doctor` warn when alias paths look wrong
- Rule path aliases are resolved before evidence collection and prompt generation
- Existing `rules-config.json` inheritance behavior remains compatible

---

## v0.6.1: Audit UX And Lightweight Metrics

### Goal

Make AI-RULES easier to understand before users hand the prompt to an AI agent.

### Scope

- Add `audit --summary`
- Add `audit --dry-run`
- Implement minimal `count` detect mode:
  - `function-lines`
  - `params-count`
- Add first rules that use `thresholds`
- Document the new audit modes and count behavior

### Non-Goals

- Do not implement cyclomatic complexity yet
- Do not implement nesting depth yet
- Do not introduce AST parsing yet
- Do not add a dynamic severity DSL

### Suggested CLI Behavior

`audit --summary` should print:

- stack
- enabled rule count
- local-evidence rule count
- AI-only rule count
- total local evidence matches
- suppressed file count from `exceptions`
- configured thresholds

`audit --dry-run` should print:

- included file patterns
- excluded file patterns
- rule IDs that will run locally
- rule IDs that require AI judgment
- exception patterns that will be applied

### Acceptance Criteria

- Users can understand audit coverage without reading the full generated prompt
- `count` rules work without AST
- `thresholds` become actively used by at least two rules
- Tests cover summary output, dry-run output, and count evidence collection

---

## v0.6.2: Report And Evidence Loop Hardening

### Goal

Make the `audit -> report -> validate-report -> fix` loop more stable and easier to automate.

### Scope

- Add stable `evidenceId` values to audit context
- Allow AI reports to reference `evidenceId`
- Improve `validate-report` to check evidence references when context is available
- Improve `fix --all` ordering:
  - `FATAL` before `WARN`
  - group same-file issues together
  - preserve rule grouping when `--group-by-rule` is used
- Add report grouping options:
  - by severity
  - by rule
  - by file
- Add a small report fixture test suite

### Non-Goals

- Do not auto-apply code changes
- Do not require AI reports to always reference local evidence
- Do not make report validation depend on a specific AI provider

### Acceptance Criteria

- Evidence generated by `audit --dump-context` can be referenced in report entries
- `validate-report` can distinguish schema drift from weak evidence linkage
- `fix --all` produces deterministic, reviewable repair prompts
- Existing reports without `evidenceId` remain compatible

---

## v0.7.0: JS/TS AST Foundation

### Goal

Move selected frontend rules from AI-only guidance toward stronger deterministic local evidence.

### Scope

- Add a JS/TS AST parsing layer
- Keep the AST API internal and narrow
- Implement first AST-backed rules for:
  - `dangerouslySetInnerHTML`
  - `eval()` / `Function()`
  - React list index key
- Add an AST-backed evidence mode that still feeds AI audit prompts
- Add a narrow call-chain proof-of-concept for:
  - UI component directly invoking fetch/axios/request-like calls

### Non-Goals

- Do not build a generic AST query DSL yet
- Do not support every language
- Do not promise full call graph accuracy
- Do not replace AI semantic judgment

### Acceptance Criteria

- AST parsing is isolated behind a small module boundary
- AST evidence has tests and clear fallback behavior
- At least one existing AI-only frontend rule gains deterministic candidates
- Medium-size repositories remain reasonably fast to scan

---

## v0.7.1: Count And AST Refinement

### Goal

Improve evidence quality after the first AST layer lands.

### Scope

- Add safer structural metrics:
  - nesting depth if AST support is stable
  - simple branch count if accuracy is acceptable
- Reduce false positives in frontend security rules
- Add evidence source metadata:
  - `local-regex`
  - `local-import`
  - `local-count`
  - `local-ast`
  - `ai-only`
- Improve prompt wording to explain evidence confidence

### Non-Goals

- Do not introduce a free-form rule language
- Do not expand into enterprise templates yet

### Acceptance Criteria

- Evidence output clearly identifies source and confidence
- Count and AST rules can coexist in one audit context
- False-positive reduction is measurable through fixtures

---

## v0.8.0: Template Ecosystem Expansion

### Goal

Expand AI-RULES from built-in templates toward a reusable rule-pack model.

### Scope

- Add one JS/TS backend template:
  - `nodejs-express`, or
  - `nodejs-nestjs`
- Add a rule-pack loading convention
- Add docs for authoring rule packs
- Add exportable rule documentation:
  - enabled rules
  - rule severity
  - detection mode
  - AI-only vs local evidence support

### Non-Goals

- Do not promise compliance certification
- Do not add many templates at once
- Do not add plugin APIs before rule-pack loading is proven

### Acceptance Criteria

- New templates reuse existing parser/config/evidence layers
- Rule-pack authoring is documented with examples
- Users can generate a readable rule catalog for a project

---

## v0.8.0+: Enterprise And Platform Track

### Goal

Explore larger organizational governance use cases without over-promising compliance.

### Possible Scope

- `security-base` rule pack
- `privacy-base` rule pack
- enterprise-oriented rule baseline
- plugin architecture
- CI-oriented command output
- SARIF-like export after report schema matures

### Framing

Use careful language:

- "compliance-informed"
- "governance baseline"
- "security/privacy rule pack"

Avoid language like:

- "SOC2 compliant"
- "GDPR compliant"
- "HIPAA compliant"

## 5. Recommended Immediate Next Step

Start with `v0.6.1` in this order:

1. Implement `audit --summary`.
2. Implement `audit --dry-run`.
3. Add `count:function-lines`.
4. Add `count:params-count`.
5. Add threshold-backed rules that use those count modes.
6. Update README and tests.

This sequence gives users visible value before the deeper AST work begins.

---

## 6. Version Exit Checklist

Every version should satisfy:

- user-facing behavior is documented
- config changes are merged through `extends`
- new detection behavior has tests
- templates parse successfully
- report/fix compatibility is preserved
- `npm test` passes
